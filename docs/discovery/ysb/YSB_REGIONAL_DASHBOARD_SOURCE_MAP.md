## 2. 可形成的时间 × 商家粒度

- 最稳的直接粒度：`month × merchant`，来源是销售额统计（按月）长表。
- 更长历史的候选粒度：`merchant × month`，来源是商业每月GMV宽表，将 `aYYYYMM` 展开即可；但必须保留“空值”和“0”的区别。
- `date × merchant`：当前区域汇总资料中没有稳定、完整的日期×商家主表；销售额统计（按日）虽然存在商家和日期，但不同文件是快照/版本，不能直接拼成连续历史。

## 3. 商家覆盖与月份覆盖

- 主推荐近期表：91 家商家、4 个月（2026-03 至 2026-06）。
- 历史 GMV 宽表候选：最多 112 个供应商 ID、41 个月列（2023-01 至 2026-05）；历史月实际非空约 99 家，不能简单宣称 112 家全覆盖。
- 最新宽表文件：43 个月列（2023-01 至 2026-07），但仅 34 家左右的筛选子集，不能作为区域完整主表。
- 以最佳近期月表与 2026-05-25 GMV 宽表做名称标准化比对：91 家月表商家中 85 家能与宽表名称匹配，6 家仅出现在月表，宽表另有 27 家；因此名称可做 staging 关联，但仍需保留未匹配清单和人工映射状态。

## 4. Target / Actual 关系

区域文件存在整体/人员级 KPI 目标，也存在商家级实际经营数据；当前未证明它们可以用同一 `period + region/owner + merchant` 粒度直接关联。商家级 target 暂时标记 `BLOCKED/PARTIAL`，不填充为 0。

## 5. staging 商家键结论

V1 可以使用：

`merchant_natural_key = normalize(供应商ID) if present else normalize(供应商名称)`

但必须保留原始 ID、原始名称、来源文件和版本，并把名称兜底标记为 `NATURAL_KEY_UNVERIFIED`。不需要等待正式 `merchant_id` 才开始 Dashboard A 的 staging 验证。
